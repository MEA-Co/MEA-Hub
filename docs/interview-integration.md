# 모의 면접 구현 및 실행 안내

갱신일: 2026-10-28 · TXT 보관·선택 느낀점·통합 도입 질문 반영

## 학생 화면

활동 입력과 면접을 별도 탭으로 구분했습니다. 활동 입력에서 작성한 내용은 면접 탭으로 이동해도 유지됩니다. 면접 도중에는 활동 정보가 읽기 전용이므로 질문 생성에 사용한 내용이 바뀌지 않습니다. 작성 중인 면접 답변도 탭 이동 시 유지되고, 입력 탭을 보고 있어도 마지막 1분 알림은 나타납니다.

활동 하나는 다음 다섯 묶음으로 입력합니다.

| 입력 항목       | 처리                                                             |
| --------------- | ---------------------------------------------------------------- |
| 학년            | 1·2·3학년 선택                                                   |
| 영역/과목       | 자율·동아리·진로·교과 세특·주요 활동 선택, 과목명 추가 입력 가능 |
| 주제(제목)      | 최대 100자                                                       |
| 핵심내용        | 역할·과정·구체적인 사실, 최대 2,000자                            |
| 느낀점/알게된점 | 선택 입력, 없으면 빈칸, 최대 1,000자                      |

면접 시작에는 **창체·세특·주요 활동 합계 10개 이상**이 필요합니다. 창체 9개는 별도 필수 조건이 아닙니다. 각 항목의 제목과 핵심내용 20자 이상을 확인합니다. 느낀점은 비워도 되고 최소 글자 수가 없습니다. 전체 핵심내용과 느낀점의 합계는 60,000자 이내입니다. 미완성 입력이나 10개 미만 활동도 TXT로 보관할 수 있습니다.

학생은 직접 작성하거나 제공되는 정리 프롬프트를 외부 AI에서 사용할 수 있습니다. 검토한 활동 요약 TXT를 붙여넣어 가져오며 원본 PDF·이미지 업로드는 제공하지 않습니다. 도우미 프롬프트도 같은 TXT 형식을 출력하도록 안내하고 없는 느낀점은 만들어내지 않습니다.

기존 생기부 업로드 메뉴는 숨겼고 `/record`에 직접 접근해도 `/interview`로 이동합니다. 코어의 기존 `/api/record`는 다른 사용처를 위해 유지했으나 이번 면접 흐름에서는 호출하지 않습니다. 원문 문서 표제 일부를 거부하는 검사를 제공하지만 모든 원문·개인정보를 완벽히 탐지하는 기능은 아닙니다.

## TXT 보관과 가져오기

활동 DB 저장 버튼·불러오기 버튼·자동 저장 상태 확인 호출을 면접 페이지에서 제거했습니다. 입력은 페이지 메모리에 유지되며, 필요할 때 **활동·특이사항 TXT 저장**을 누른 뒤 파일 내용을 **TXT 붙여넣기로 가져오기**에 붙여넣어 재사용합니다. 새로고침 전 보관이 필요합니다. 면접 결과도 **결과 TXT 저장**으로 내보내며 JSON 내보내기 UI는 제공하지 않습니다.

`_lib/preparation-text.ts`가 읽을 수 있는 한국어 필드 형식의 TXT를 생성·검증합니다. JSON에 txt 확장자만 붙이는 방식이 아닙니다. 줄마다 `| `를 붙여 멀티라인과 필드명·구분자가 실제 내용 안에 들어가도 혼동하지 않습니다. 활동의 식별자와 미완성 필드, 선택/미선택 특이사항의 작성 중 값도 왕복합니다. 최대 200,000자, 활동 60개, 기존 필드 상한과 명백한 원문·개인정보 차단을 적용합니다.

- 가져오기는 파싱·검증에 모두 성공한 뒤 활동과 특이사항을 함께 반영합니다. 잘못된 입력은 현재 내용을 바꾸지 않습니다.
- TXT에 특이사항 섹션이 없으면 현재 특이사항을 그대로 둡니다. 섹션이 있으면 파일의 선택 상태와 작성 내용을 반영합니다.
- 면접 중에는 활동·특이사항 편집과 가져오기를 막고, 보관용 내보내기는 허용합니다.
- 기존 저장 API·DB 코드는 호환을 위해 남겨두지만 면접 UI에서는 호출하지 않습니다. 기존 DB 자료를 삭제하거나 새 DB 연결을 추가하지 않았습니다.

## 면접 진행

시간은 3~20분, 기본 10분이며 양쪽에서 범위를 검증합니다. 남은 시간 표시, 통합 도입 질문 연습, 마지막 한마디를 선택합니다. 도입 질문 연습을 켜면 자기소개·지원동기·진로/학습계획 중 하나를 서버가 무작위로 제시합니다. 단순 관심 표명에는 후속을 강요하지 않으며, 자발적으로 설명한 활동·선택·주장에 아직 확인할 만한 근거가 있을 때만 최대 두 번 이어 묻습니다. 충분히 설명했거나 확인할 지점이 없으면 바로 다른 질문으로 전환합니다. 첫 질문이 완성되면 시간이 시작됩니다. 타이머를 숨겨도 마지막 1분에는 알림을 표시하며, 마지막 한마디 선택 시 마지막 1분의 다음 질문으로 제시합니다. 마지막 답변 제출 또는 시간 만료·수동 종료 시 질문·답변 목록과 한 문단 피드백을 정리합니다. 작성 중 답변과 미답변 질문도 결과에 남깁니다.

채팅은 항상 사용할 수 있습니다. 클로바 실시간 게이트웨이가 설정되면 녹음 중 인식된 문장을 답변 칸에 표시합니다. 브라우저 AudioWorklet이 마이크 음성을 16kHz·모노·16비트 PCM으로 바꾸고 약 100ms 단위로 Core WebSocket에 보냅니다. 녹음 완료를 누르면 마지막 음성 조각을 전송하고 최종 문장을 확인합니다. 최대 녹음 시간은 2분입니다.

녹음 전 작성한 답변은 유지하고, 중간 결과와 최종 결과는 동일한 음성 부분을 갱신하므로 중복해서 붙지 않습니다. 녹음 중에는 직접 편집·제출을 잠시 막고, 완료 후 학생이 내용을 수정해 직접 제출합니다. 연결 오류·취소·시간 초과가 발생해도 이미 인식된 답변은 남습니다. 탭 이동·면접 종료 시 마이크와 연결을 정리합니다.

AudioWorklet을 지원하지 않는 브라우저나 HTTPS 파일 인식만 설정된 Core에서는 기존의 녹음 완료 후 WAV 전송 방식을 사용하며 화면에 이를 안내합니다. 음성 실패 시 채팅으로 계속할 수 있습니다. 질문 음성 재생은 이번 범위에 포함하지 않았습니다.

## 클라이언트와 서버 구조

```text
Hub /interview
  활동 입력 탭 → 활동 다섯 필드 + 선택 특이사항 ↔ TXT 내보내기/붙여넣기
  면접 탭 → 설정 → 스트리밍 질문·답변 → 결과

Hub /api/interview/stream → Core /api/interview/stream → OpenAI
브라우저 AudioWorklet → Core /api/interview/speech (WebSocket) → CLOVA gRPC
Hub /api/interview/transcribe → Core /api/interview/transcribe → CLOVA (일괄 인식 대체 경로)
Hub /api/interview/capabilities → Core 기능 설정
```

활동의 핵심내용(core_content)과 선택 느낀점(reflection)은 API·TXT·AI 프롬프트에서 별도 필드로 유지합니다. 기존 간단한 면접관 프롬프트를 기반으로 활동과 최근 답변을 근거로 후속 질문을 만듭니다. 새 클라이언트는 ask_intro 하나를 보냅니다. 도입 기본 질문은 서버 템플릿 중 하나이고 후속 질문의 관점은 서버가 정합니다. kind는 self_introduction/motivation/learning_plan, strategy.source=intro와 depth=0~2로 이력을 보존합니다. 기존 ask_self_introduction/ask_motivation은 구버전 요청 호환용 선택 필드로 유지합니다. 마지막 한마디는 선택에 따라 제시합니다. 기본 모델은 비용·속도를 우선한 gpt-6-luna이며, 추론을 끈 reasoning_effort=none 설정을 사용합니다. 질문 생성과 최종 평가에 동일하게 적용하며 INTERVIEW_MODEL로 변경할 수 있습니다.

면접 요청에는 설정·활동·답변 이력을 보내므로 서버 메모리 세션에 의존하지 않습니다. 긴 면접은 AI에 전달하는 문맥만 제한하고 결과에는 전체 이력을 유지합니다. 질문·평가에는 OpenAI로 요약과 답변을, 음성 인식에는 CLOVA로 녹음을 전달합니다. 앱은 이 내용을 로그에 출력하지 않습니다.

## 설정 및 로컬 실행

| 위치 | 환경변수                                          | 용도                                                      |
| ---- | ------------------------------------------------- | --------------------------------------------------------- |
| Hub  | CORE_API_URL                                      | 코어 기본 주소. 기존 NEXT_PUBLIC_BACKEND_ORIGIN보다 우선  |
| Hub  | INTERVIEW_SPEECH_WS_URL                           | 선택 사항, 브라우저가 연결할 공개 Core WebSocket 주소      |
| Core | ALLOWED_ORIGINS                                  | Hub의 정확한 Origin 목록, 쉼표로 구분                      |
| Core | OPENAI_API_KEY                                    | 실제 질문 생성·평가                                       |
| Core | INTERVIEW_MODEL                                   | 선택 사항, 기본 gpt-6-luna                                    |
| Core | INTERVIEW_DEMO_MODE=true                          | 실제 AI를 호출하지 않는 명시적 예시 모드                  |
| Core | CLOVA_SPEECH_INVOKE_URL / CLOVA_SPEECH_SECRET_KEY | 음성 인식, 기존 CLOVA_HOST / CLOVA_SECRET_KEY 이름도 지원 |
| Core | INTERVIEW_DATABASE_URL                            | 기존 저장 API용. 현재 면접 화면에서는 사용하지 않음       |

기존 CLOVA_HOST가 공식 실시간 게이트웨이 주소(포트 50051)이면 gRPC로 연결하고, HTTPS Invoke URL이면 기존 파일 인식 방식으로 연결합니다. gRPC에는 grpcio와 protobuf가 필요합니다. 제공자 설정 승인을 받은 후 마이크 전송을 시작하며, 마지막 전송의 완료 확인 후 남은 결과까지 수신합니다. 실시간 경로에서는 짧은 문장도 중간에 표시되도록 durationThreshold=3000, gapThreshold=500, useWordEpd=true, usePeriodEpd=false를 사용합니다.

Core capabilities의 speech_streaming이 true이면 Hub가 speech_websocket_url을 추가합니다. 기본값은 CORE_API_URL에서 유도하며, Core가 사설 네트워크에 있으면 INTERVIEW_SPEECH_WS_URL에 브라우저가 접근 가능한 공개 주소를 별도로 지정해야 합니다. 이 주소에는 비밀키나 쿼리 인증 정보를 넣지 않습니다. HTTPS Hub에서는 WSS 연결이 필요하며, WS만 있으면 일괄 인식 경로를 안내합니다. Core는 ALLOWED_ORIGINS와 일치하는 브라우저 연결만 수락합니다.

코어는 .env를 읽습니다. 비밀키를 브라우저 코드나 공개 환경변수에 넣지 않습니다. 실제 호출 검증에서는 기존 키를 서버 프로세스에서만 읽고 복사·출력하지 않았습니다.

```sh
# mea-core
.venv/bin/python -m pip install -e '.[dev]'
ALLOWED_ORIGINS=http://localhost:3001,http://127.0.0.1:3001 .venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --reload --port 8000

# MEA-Hub: 별도 터미널
CORE_API_URL=http://127.0.0.1:8000 npm run dev -- --hostname 127.0.0.1 --port 3001
```

http://127.0.0.1:3001/interview 에서 사용할 수 있습니다. 현재 면접 화면의 입력 보관에는 DB 설정이 필요하지 않습니다. 디자인은 면접 페이지 안에만 적용하고 로고·상단 메뉴·결과 버튼을 통한 다른 허브 영역 이동은 제공하지 않습니다. 홈과 다른 허브 페이지는 변경하지 않습니다.

## 배포 제약

기존 코어는 API Gateway HTTP API + Mangum + Lambda 30초 구성입니다. 이 방식은 응답 조각을 모아 반환하므로 실시간 스트리밍 운영에는 기존 Dockerfile의 Uvicorn 실행 방식이나 별도 응답 스트리밍 배포가 필요합니다. Hub CORE_API_URL을 해당 주소로 지정해야 합니다. 실시간 음성은 브라우저에서 Core로 지속적인 WebSocket을 열므로, 기존 HTTP API Gateway + Mangum 경로로는 제공되지 않습니다. Uvicorn을 실행하는 서버와 WebSocket 업그레이드를 지원하는 프록시가 필요합니다. 프록시는 최소 160초 연결을 유지하고 HTTPS 환경에서는 WSS를 제공해야 합니다. 이번 작업에서 운영 서버를 배포하거나 DB 연결 정보를 임의로 추가하지 않았습니다.

Hub는 질문마다 요청하며 스트리밍 프록시 실행 설정은 120초, 연결 제한은 100초입니다. DB 프록시는 20초 제한을 사용합니다. 기존 Lambda 템플릿에는 AI·CLOVA 비밀키나 DB 주소 주입이 없으므로 운영 환경에서 별도로 설정해야 합니다.

Core의 `app/interview/policy.py`가 12개 관점과 템플릿, 활동 분산, 후속 질문 깊이를 결정합니다. 관점은 탐구 출발점/본인 역할/개념 이해/근거·검증/문제 해결/성찰 변화/협업 기준/관심·진로 연결/적용·확장/대안·반대/한계·재설계/범위 확인입니다. 다음 질문을 위한 별도 AI 분류 호출은 추가하지 않았습니다.

기본 질문 뒤 같은 활동의 후속 질문은 최대 두 번이며, 이후 덜 다룬 활동·영역·학년으로 전환합니다. 남은 90초에는 복잡한 새 쟁점보다 짧은 성찰을 우선하고, 기존 마지막 1분·마지막 한마디 선택 규칙은 그대로 우선합니다. 횟수와 시간 기준은 영상의 주장이 아닌 제품 운영 정책입니다.

답변의 한계/실패/협업/근거/변화 관련 표현은 질문 후보를 고르는 단서일 뿐 점수·역량 판정이 아닙니다. 같은 관점을 반복하지 않고 실제 답변을 읽어 질문을 구체화하도록 AI에 지시합니다. 모른다는 답변은 범위 확인을 한 번 제공하고 재차 어렵다고 하면 다른 활동으로 전환합니다. 단순 표현 규칙이므로 모든 의미·부정·과거 인용을 완벽히 이해하지는 못하며, 질문의 구체화와 최종 평가는 모델 출력의 품질에 영향을 받습니다.

`Question`/`Turn`에는 선택적 `strategy={version,activity_id,focus,depth}`가 추가됩니다. `kind`는 기존 네 값을 유지합니다. Hub는 제출·시간 만료 시 작성 중 답변·미답변 질문에 이 정보를 보존하며 결과 화면과 내보내기에 질문 유형을 표시합니다. 상태는 요청의 이력에서 매번 복원하므로 특정 서버 메모리에 의존하지 않습니다. 실제 연속 이력으로 깊이를 계산하며 클라이언트의 depth를 횟수로 신뢰하지 않습니다. 구형·알 수 없는 활동 ID의 이력은 사실을 추정하지 않고 분산용 가상 슬롯만 계산합니다.

평가는 탐구 이해/본인 역할/논리·대안·문제 해결/성찰/협업/관심 확장 여섯 관점을 내부 기준으로 사용합니다. 실제 답변에서 관찰한 근거와 관찰하지 못한 부분을 구분하고, 근거 있는 강점 하나·가장 중요한 보완점 하나·다음 연습 행동을 4~6문장 한 문단으로 작성합니다. 학생 요약이나 질문 자체를 실제 답변한 성취로 취급하지 않습니다. 점수·합격 가능성·공식 대학 평가표·음성·외모·태도를 판정하지 않습니다. 결과 화면의 접이식 ‘피드백 기준’에서 같은 기준을 볼 수 있습니다.

성적, 특정 대학 교육과정, 최신 시사는 입력에 없으므로 질문의 사실 전제로 만들지 않습니다. 새 디테일을 거짓말로 단정하지 않고, 실제 상충이 있는 경우에도 활동·단계의 차이를 중립적으로 확인하도록 합니다. 전공과 직접 관련 없는 활동도 배제하거나 억지로 연결하지 않습니다.

AI 지침은 [OpenAI 공식 프롬프트 구성 안내](https://developers.openai.com/api/docs/guides/prompt-engineering)에 따라 입력 자료와 지시를 분리하고 대표 회귀 사례로 검증했습니다. 기본 GPT-6 Luna와 질문·평가 각 한 번의 모델 호출, 기존 실시간 음성 경로를 유지합니다.

## 선택 특이사항과 서버의 일반 경험 질문 혼합

활동 입력 탭의 ‘면접에 참고할 특이사항’에서 성적 관련 상황을 최대 3개, 진로 변경을 선택 입력합니다. 성적은 과목 또는 학년·학기와 짧은 상황 설명을 받고 등급·점수를 요구하지 않습니다. 진로는 이전 관심 분야·현재 관심 분야와 선택 설명을 받습니다. 해당하지 않는 그룹은 보내지 않으며 빈 선택 폼은 면접을 막지 않습니다. `circumstances`는 선택적인 요청 필드이며 시작 시 복사한 값을 답변·종료 요청에도 전달합니다.

서버는 실제 활동 답변 세 개 이상이 오간 활동 전환 지점, 남은 시간 120초 이상에서 관련 특이사항을 우선하거나 표집합니다. 정확히 언급한 과목·분야를 일반적인 학습·진로 표현보다 우선하며 이미 물은 사항, 연속 특이사항, 총 두 건 초과는 제외합니다. 모든 입력을 반드시 질문하지 않습니다. 특이사항을 입력했다는 이유로 평가하지 않으며 해당 질문에 실제로 답한 내용만 피드백 근거로 사용합니다.

별도로 의미 있었던 활동·실패 경험·협력/갈등 해결·리더십 경험의 일반 질문을 서버가 무작위 순서로 섞습니다. 학생이 유형을 선택하는 설정이나 체크박스는 없습니다. 활동 목록 밖의 실제 경험도 말할 수 있으며 경험이 없으면 다른 질문으로 이동합니다. 일반 질문 뒤에는 실제 답변을 바탕으로 최대 두 번 꼬리질문하고 다시 활동 질문으로 돌아갑니다. 현재는 한 면접에서 일반 질문 두 유형까지, 활동 답변 세 개 이상 후 충분한 시간이 있는 전환 지점에서 넣습니다. 특이사항과 일반 질문이 연속으로 개입하지 않도록 합니다.

일반 질문의 첫 문장은 서버 템플릿이므로 모델 호출이 없고, 구체적 꼬리질문에는 기존 모델 호출 한 번만 사용합니다. 학생에게 실패·갈등·리더 직책이 있다고 가정하거나 모범 경험을 만들어 답하도록 요구하지 않습니다. 일반 경험이 없다는 사실로 역량 부족을 단정하지 않습니다.

`strategy.source`는 activity/circumstance/general/intro를 구분합니다. 일반 질문은 `general_topic`, 특이사항은 `circumstance_id`로 이어받으며 해당 질문에는 활동 ID를 가정하지 않습니다. `mix_seed`는 첫 질문 때 서버가 발급하는 공개 난수입니다. 새 면접마다 새로 발급하며, 같은 면접의 이력에 보존해 재시도 시 질문 선택을 재현합니다. 비밀키·인증용 토큰이 아닙니다.

활동 전환은 새 활동 제목을 명시하도록 지시합니다. 모델이 제목을 누락하면 최종 질문을 해당 활동의 안전한 템플릿으로 대체합니다. 스트리밍 토큰은 준비 중 문구이며 최종 question 이벤트가 확정 질문입니다. 이 검사는 제목 누락을 잡는 구조 검사이고 모든 의미적 정확성을 보장하는 판정기는 아닙니다.

특이사항은 활동과 함께 준비 TXT에 보관할 수 있습니다. 면접을 시작할 때 선택한 유효한 값의 사본을 만들어 질문 요청에 전달합니다. 결과 화면의 TXT는 질문·답변과 피드백을 보관하는 용도이며 준비 TXT와 형식이 다릅니다. 탭 이동과 다시 연습하기에서는 입력을 유지하지만 페이지 새로고침 후 복구하는 자동 저장은 제공하지 않습니다. 개인정보나 생기부 원문은 입력할 수 없습니다.

## 2026-10-28 후속 질문·재시도 품질 보강

새 품질 회귀 사례를 통해 일반 경험 질문의 답변 처리를 보강했습니다. ‘실패한 적은 없습니다’, ‘리더를 맡아 본 적이 없습니다’, ‘없어요’ 등은 없는 경험에 대한 후속 질문으로 이어가지 않습니다. 반면 부족한 부분을 인정한 뒤 실제로 한 대체 행동을 설명하거나 과거의 모름을 행동으로 해결했다면 그 실제 경험은 유지합니다. 미래에 해보겠다는 계획만으로 과거 경험이 있었다고 처리하지 않습니다. 부정된 실패·갈등 표현은 질문 후보 선택에서 제외하고, 생활 경험의 기본 후속 관점에는 교과 개념 퀴즈를 넣지 않습니다. 표현 규칙은 대표 문장을 처리하는 보조 수단이며 모든 한국어 문맥을 완벽히 판단하는 분류기는 아닙니다.

AI에 전달하는 긴 문답은 앞부분과 끝부분을 예산 안에서 함께 남깁니다. 긴 면접 평가에는 가장 최근 답변을 위한 추가 공간을 확보합니다. 명시적으로 정정한 설명을 우선하고 철회한 앞말을 성취로 평가하지 않도록 질문·평가 지침에도 반영했습니다. 원본 질문·답변과 결과 내보내기의 전문은 그대로 유지합니다. 중간 내용은 예산 때문에 생략될 수 있습니다.

Hub의 종료 평가 재시도는 최초 종료 요청의 시간·종료 방식을 그대로 사용합니다. 수동 종료 후 응답 실패·대기를 거쳐 재시도해도 그 대기시간이 면접 시간에 더해지거나 시간 종료로 바뀌지 않습니다. 답변 요청의 재시도는 수정한 현재 답변을 사용하며, 음성 준비·녹음·마지막 문장 인식 중에는 오류 상자의 재시도 버튼도 막아 부분 인식만 제출되는 일을 방지합니다.

검증은 가상 생활 경험의 실제 후속 질문과 정정 답변의 실제 평가, 거절·대체 경험·예산 제한·원본 불변성, 실제 hook의 종료 재시도와 실제 컴포넌트의 음성 재시도 상태를 포함합니다. 별도의 질문 유형 선택 설정, 추가 AI 분류 호출, DB 저장 형식 변경은 추가하지 않았습니다.
